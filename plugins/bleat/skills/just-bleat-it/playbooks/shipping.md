### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

This is the half after `playbooks/babysit.md`.

1. **Verify each PR independently before it lands.** One verifier per PR, each a subagent in its own worktree, runs the change the way a user would (the `verify` skill for UIs, `run` for CLIs and TUIs), parent against head, and posts `PASS`, `PASS+NOTES`, or `FAIL` on that PR. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. **Arm merge-when-ready through Graphite, and pass `--always`.** Arm only a run whose verdicts cover the current heads, because merge-when-ready lands whatever head is ready. A no-op submit skips the Graphite update and silently arms nothing, which reads exactly like success.
   ```bash
   gt submit --merge-when-ready --always --update-only --no-interactive
   ```
   Never enable GitHub auto-merge on a stack. Only the root targets protected trunk. Every child targets its unprotected parent branch and already reads `CLEAN`, so GitHub would merge children into parents immediately and collapse the stack into itself. If a previous agent armed it, disarm with `gh pr merge <n> --disable-auto` and confirm the field is back off. Do not read `autoMergeRequest` as proof that merge-when-ready is armed. It stays off until Graphite reaches that PR at the queue front. Confirm arming from Graphite's own state, and if you cannot, say so rather than inferring it. Read each landed PR back (`gh pr view <pr> --json state,mergedAt,baseRefName`), because a queued or requested merge is not a merge. A landed PR reads merged with trunk as its base.
5. **Leave the stack alone while it lands.** No `gt sync`, no restack, no speculative pushes, and no `gt submit --stack`, which reaches downstack into PRs that are mid-merge, because a merge lands whatever its branch and base hold at that moment, verdict or not. Even a plain `gt submit` can retarget a base if local Graphite tracking has diverged, so never run `gt` from a worktree whose parentage you have not just checked. Watch the run with the queued watcher from `playbooks/babysit.md` (`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>`) under `/loop` until it reports `COMPLETE` at the ceiling. Bases retarget and `graphite-base/*` refs get cut as each PR merges. That is Graphite working, not damage to repair. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what you armed and how you confirmed it, what landed, and what the next gap needs.
